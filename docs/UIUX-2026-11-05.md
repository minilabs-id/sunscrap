## 3. Arsitektur renderer terkini

```
src/renderer/
├── index.html        # shell, CSP script-src 'self'
├── format.js         # 20 helper murni (fmt, delta, esc, …) — UMD: global + CommonJS (teruji)
├── store.js          # createState + helper state murni (pagination/sort/density/review/signature)
├── app.js            # DOM render + binding
└── styles.css        # design tokens + komponen
```

- **Tanpa framework, tanpa bundler, tanpa dependensi runtime** — tetap patuh CSP `script-src 'self'`.
- `format.js` & `store.js` memakai pola *dual-mode* (global `window` untuk renderer, `module.exports` untuk `node --test`).
- State = satu objek `createState()`; logika turunan (sort/pagination/review/fingerprint) murni dan teruji.

## 5. Keputusan GATE — vanilla vs adopsi build step

**Keputusan: tetap VANILLA (tidak mengadopsi Vite/framework) untuk saat ini.**

Alasan (berbasis bukti setelah seluruh Fase):
1. **Ukuran/cakupan tidak menuntut framework** — renderer hanya 3 file; logika murni sudah dipisah & teruji; `state` sederhana sudah cukup. Tidak ada reactive-state lintas-panel yang menyakitkan.
2. **Hot-path sudah dioptimasi** (render gate), yang sebelumnya jadi biang keluhan performa — bukan "butuh framework".
3. **Resiko migrasi tinggi, nilai rendah** — adopsi Vite+framework berarti rewrite renderer + ubah packaging/CSP/CI untuk tool solo yang sudah jalan.
4. **Batasan tetap terpenuhi & aman** — CSP `self`, tanpa dependensi runtime.

**Kapan re-evaluasi (trigger):**
- Jumlah view/komponen interaktif tumbuh signifikan (mis. > 20) sehingga vanilla mulai sulit dirawat.
- Muncul kebutuhan state-reaktivitas kompleks antar banyak panel secara live.
- Ada rencana berbagi komponen lintas-proyek.

**Perantara bila butuh "build-step lite"**: tambahkan `esbuild` sebagai langkah *produksi* untuk minify/bundle 3 file renderer (satu baris, tanpa framework) — belum dilakukan karena nilainya marginal saat ini.
